# Парсинг учасників конференцій

Скіл збирає учасників із API подій у CSV. Працює лише із запитами, які користувач сам скопіював зі своєї авторизованої сесії (DevTools → Network → Copy as cURL, або Proxyman для мобільного застосунку). Сервіс не навантажуємо і автоматизацію не маскуємо.

## Правила (чому саме так)

- **Строго послідовно, пауза 3–5 с з джитером.** Паралельні запити схожі на атаку; повільний прохід нікому не шкодить. Це вже вбудовано в скрипти.
- **Зупинка, а не обхід:** 429 → стоп і доповісти; 401/403 → стоп (токен протух або доступу немає; не ротуємо токени/IP/заголовки); два 5xx або два збої мережі підряд → стоп. Агресивних ретраїв немає.
- **Не маскуємо автоматизацію.** Не підміняємо user-agent, відбитки, не крутимо проксі, не обходимо CAPTCHA/anti-bot. Якщо користувач просить «щоб не було видно, що парсимо», пояснити, що цього не робимо; швидкість і ввічливість (правила вище) — це все, що потрібно. Заголовки беремо як є з curl користувача.
- **Кожна сторінка зберігається окремим JSON і не запитується двічі.** Перезапуск продовжує з місця зупинки.
- **Токени не друкуємо** у відповідях, логах і CSV. Вони лише в `config.json` (права 600). Користувач вставляє curl у чат — у відповідях показуємо тільки приховане (`access-token: Dpvw…`).
- **Мінімум запитів.** Спочатку розвідка (1 запит на варіант із `page[size]=1`), потім повний прохід. Не робимо зайвих запитів «на всяк випадок».

## Робочий процес

1. **Робоча тека.** Використати scratchpad сесії (`…/scratchpad/<подія>/`). Увага: scratchpad між сесіями/днями **очищується** — не розраховувати, що старі дампи збережуться. Для «залиш тільки нових» треба просити в користувача файл зі старим списком (див. крок 6).
2. **Конфіг із curl.** Зберегти вставлений curl у файл і виконати:
   `python3 ~/.claude/skills/conference-leads-parser/scripts/curl_to_config.py --curl-file curl.txt --out work/config.json`
   Скрипт викидає трекінг-заголовки (sentry, baggage, sec-*, cookie, if-none-match), приховує секрети у виводі. Номер сторінки з curl ігноруємо — завжди йдемо з першої. Якщо в curl є `--proxy http://localhost:…` — це проксі користувача для перехоплення, він не потрібен (скрипт його відкидає).
3. **Визначити платформу за URL** і піти відповідною гілкою нижче.
4. **Прохід у фоні** (Bash `run_in_background`, timeout 600000). Фонова задача живе максимум 10 хв, тому скрипти самі зупиняються на `--max-seconds 540` і пишуть, як продовжити. Для великих подій (сотні сторінок) це 2–3 запуски. Після завершення задачі перевірити лог і що немає пропущених сторінок. Продовження після ліміту — повторити ту саму команду (`--start auto`); якщо система просить не перезапускати задачу з максимальним таймаутом — повідомити користувача й запустити за його підтвердженням («продовжуй»).
5. **CSV** відповідним build-скриптом. Показати користувачу підсумок: скільки всього, скільки joined/registered, скільки з LinkedIn/email, і файл віддати через SendUserFile.
6. **Виключення відомих лідів.** Попросити CSV/XLSX з уже опрацьованими (колонка з id: `registrant_id` / `attendee_id` / `participant_id`; з xlsx — прочитати openpyxl, зібрати id з усіх аркушів) і передати `--exclude`. Скрипт каже, скільки відомих знайдено й скільки зникло з видачі (скасовані реєстрації). Сума нових = свіжа видача − відомі. Вихід може збігатися з уже надісланим файлом, якщо нових не додалось — так і сказати.
7. **Повторний запуск («дореєструвались — онови»).** Той самий конфіг у нову теку `run_<дата>`, build з `--exclude` попереднього CSV. Токен міг змінитись — тоді користувач скидає новий curl.

## Brella (`api.brella.io/api/events/<slug>/…`)

**Який ендпоінт брати** — перед повним проходом зробити розвідку:
`python3 …/brella_probe.py --config work/config.json` (5 запитів по `page[size]=1`, показує `total_count` для кожного варіанту).

Що показує практика (VDS, Wolves, Bits & Pretzels, startupfair):
- `/attendees` без параметрів — лише ті, хто в апці **і** відкритий для нетворкінгу.
- `/attendees?ignore_networking=true` — усі, хто в апці (включно з тими, хто вимкнув нетворкінг; у даних `skip-networking: true`).
- `/registrants` — усі зареєстровані, включно з тими, хто **не заходив в апку** (у них немає профілю: порожні industry/interests/контакти, `status = registered`). Це найповніший список; на VDS 3528 проти 734.
- `show_only_best_matches=true` — тільки «збіги», не повний список; для парсингу не підходить.
- Інколи `/attendees` містить людей, яких немає в `/registrants` (на VDS 44) — build-скрипт додає їх із `in_registrants_list=no`, щоб нікого не втратити.

Рекомендація: для лідгену брати **`/registrants`** (+ `/attendees?ignore_networking=true` для колонок networking/pitch/interests, якщо подія їх так віддає). Для малих подій дешево зібрати обидва й об'єднати.

Збір і збірка:
```
python3 …/brella_fetch.py --config work/config.json --endpoint registrants --out work/reg
python3 …/brella_fetch.py --config work/config.json --endpoint attendees  --out work/att
python3 …/brella_build_csv.py --registrants-dir work/reg --attendees-dir work/att --out leads.csv [--exclude old.csv]
```
Що є в даних: ім'я, посада, компанія, тип квитка (`ticket_type`, напр. Investor/Startup Founder/Speaker — дуже корисно для сегментації), `is_attendee`, `networking`, pitch, interests з intent-мітками («Invest in», «Get investment»…), email/linkedin/website/країни — **лише у тих, хто зайшов в апку і заповнив профіль** (зазвичай LinkedIn у 10–25%, email у 1–6%). Industry/function/persona є не в усіх подіях; кастомні поля реєстрації (sector, funding stage тощо) список не віддає — для них потрібен окремий запит на кожного учасника (сотні запитів, робити лише за явним «так»).

Свіжі токени: у різних сесіях/подіях `access-token` і `client` різні — беремо з curl користувача. Домен у `origin`/`referer` (`next.brella.io` або `<org>.brella.io`) і `brella-organization-slug` теж беруться з curl як є.

## b2match (`b2match.com/b2md-api/v4/query`, GraphQL)

Запит — persisted query з курсорною пагінацією (`variables.page.after`). Скрипти скидають курсор на `null` і йдуть від початку:
```
python3 …/b2match_fetch.py --config work/config.json --out work/pages
python3 …/b2match_build_csv.py --pages-dir work/pages --out leads.csv [--exclude old.csv]
```
У списку є: ім'я, посада, компанія, країна/місто, pitch, about, interests, skills, посилання на профіль і компанію. **Email і LinkedIn b2match у списку не віддає** — їх шукають окремо (скіл `sda-lead-enrichment`). Лічильник `participantsCount` у відповіді бувває трохи більший за видимий список (приховані профілі). Якщо відповідь без `data` (persisted query застарів) — попросити свіжий curl.

## Algolia (`<APPID>-dsn.algolia.net/1/indexes/*/queries`, напр. Web Summit `se_attendances_v1_production`)

Рядок `CONNECT` у Proxyman — лише тунель, даних там немає; потрібен наступний **POST** `/1/indexes/*/queries` (є `X-Algolia-Api-Key`, у тілі `requests:[{indexName, facetFilters, page…}]`). Ключ зазвичай обмежений однією конференцією й індексами (це нормально).
Головне обмеження: **максимум 1000 хітів на пошук**. `nbHits` показує реальний обсяг (на Web Summit ≈19,6 тис.), тож список ділять за фасетами (`accreditation.name`, `industry.name`, `country.name`), а дрібні значення групують через OR. `algolia_fetch.py` робить це сам і бере по 1000 записів за запит (на ~7 тис. людей вистачило 17 запитів), кешує все й відновлюється:
```
python3 …/algolia_fetch.py --config work/config.json --out work/pass1 \
   --select "accreditation.name=ALPHA,BETA,GROWTH,PARTNER,SPEAKER,EXECUTIVE" --split industry.name,country.name
python3 …/algolia_build_csv.py --pages-dir work/pass1 --out leads.csv [--exclude known.csv]
```
Спершу один запит із `hitsPerPage:0, facets:["*"]` — покаже, за якими полями можна ділити, і розподіл. Перед великим збором показати користувачу розбивку за акредитаціями (напр. ATTENDEE/ALPHA/BETA/GROWTH/PARTNER/SPEAKER/INVESTOR/MEDIA/STAFF) і запропонувати, кого брати: для лідгену SDA — стартап-квитки, партнери, спікери; інвесторів окремо; ATTENDEE — другим проходом за індустріями. У записі є ім'я, посада, компанія, індустрія, країна, bio, акредитація; **email/LinkedIn немає**.

## Slush (`search.slush.org/search/meeting-tool/<event>/all`, пошук із `searchAfter`)

POST із тілом `{options:{page:{size,searchAfter:[…]}}, target_ids:[<event>]}`; відповідь `{meta:{page:{total_results,…}, searchAfter}, results:[{user, company, meeting_fit}]}`. **Токен `Authorization` живе ~15 хв** (видно з `exp−iat` у JWT) — перевірити строк одразу й вкластися: API дозволив `size=200` (замість 24 у застосунку), тож ~10 тис. людей = 50 запитів ≈ 5 хв. Якщо токен спливе (401) — скрипт зупиняється, користувач скидає свіжий curl, продовжуємо з курсора.
```
python3 …/searchafter_fetch.py --config work/config.json --out work/pages --size 200
python3 …/slush_build_csv.py --pages-dir work/pages --out slush.csv [--exclude known.csv]
```
У записах є посада, компанія, тип компанії (startup / vc-investor / ecosystem …), країна, LinkedIn (~70%), website, bio, опис компанії, стадія, фокус інвесторів. Email немає.

## Інші REST-списки (напр. vendo-ai `…/contacts?page=&limit=`)

`generic_page_fetch.py` збирає будь-який список із `page`/`limit` у CSV, `--tag "Категорія"` додає колонку-мітку, `--append` додає рядки іншої аудиторії в ту саму таблицю (так робили «Logistics — Sweden» + «Real Estate — UK»). Спершу один запит і подивитись структуру (`contacts`, `total`, `totalPages`), потім усі сторінки.

## Типові проблеми

- **Фонова задача «killed»** — ліміт 10 хв; продовжити з місця зупинки (див. крок 4).
- **Класифікатор авто-режиму не дає вердикту / блокує** (повторюється) — не обходити: попросити користувача перемкнути режим дозволів на «Manual» (випадайка біля поля вводу) і повторити ту саму команду. Не радити «Bypass permissions».
- **curl зависає без відповіді, `HTTP 000`** — мережевий збій на боці API; повторний поодинокий запит зазвичай проходить; скрипт сам зупиняється після двох збоїв, продовжити можна `--start auto`.
- **Кількість зросла під час прогону** (реєстрація триває) — на останніх сторінках можуть бути дублікати/зсуви; build-скрипти дедублікують за id.
- **Файл користувача не відкрився / немає колонки id** — подивитись заголовки (`head -1`) і назвати колонку явно.
