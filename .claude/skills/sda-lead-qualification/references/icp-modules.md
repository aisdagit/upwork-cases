# ICP — модульний довідник SDA
> **Головний файл для людей:** `Контекст SDA/База знань про компанію/SDA — ICP & Tier Rules` (v2). Цей довідник — технічна версія для скілів; при змінах правил оновлювати обидва.

**Статус:** чернетка v0.5. Основні правила погоджено; три пункти позначені «за замовчуванням до підтвердження» (див. розділ 8).
**Зміни у v0.2:** SDA готова до enterprise-закупівель, тож MOD-5 активний без обмежень. Партнерський канал у SDA є, тож позначки Partner / Partner? передаються партнершіпу.
**Зміни у v0.5 (27.09.2026):** enterprise-гіганти (DAX/MDAX-рівень, міжнародні групи з десятками тисяч людей) — Tier 3 для всіх модулів, навіть з digital-роллю: SDA не має виходу на їхній procurement. Виняток — людина в застосунку сама шукає зовнішніх постачальників чи партнерів. Великий Mittelstand (сімейні й середні групи на 200–10 000 людей) лишається основною ціллю MOD-5.
**Зміни у v0.4:** виправлено визначення FD Engineers за сторінкою послуги SDA: виділений інженер SDA в команді клієнта доводить AI-автоматизацію до продакшну. Основні ICP — AUT-4 і MOD-5, другорядний — DEV-2.
**Зміни у v0.3:** 6 модулів залишаються, у DEV-2 додано «Тип потреби»; DEV-1 за замовчуванням вимкнено, з винятком; межі IOT-6 визначено через стек SDA; гео для AUT-4 розширено (DACH і ЄС — прийнятні); FD Engineers прив'язано до DEV-3/DEV-2; нове правило вибору основного ICP.
**Для чого:** єдине джерело правил для кваліфікації лідів (конференції, списки, LinkedIn) і основа для скіла кваліфікації. Структура така: спільне ядро для всіх лідів плюс окремий модуль на кожен ICP. Щоб додати новий ICP, треба дописати новий модуль за тим самим шаблоном, решта довідника не змінюється.

**Джерела:** «ICP — детальні профілі клієнтів MARS», «SDA — ICP & Tier Rules», «Загальна таблиця сервісів MARS», «ICP A revised — Integration та Dashboards BI», перелік послуг SDA (вересень 2026), тест фільтрації Bits & Pretzels 2026.
Позначка **[нове]** означає, що пункт з'явився в цьому довіднику і в попередніх документах його не було. Такі пункти треба підтвердити.

## 1. Як користуватися довідником

**Етап 1** (дані застосунку або списку: посада, компанія, persona, pitch, країна):
1. Застосувати **спільне ядро**. Воно відсіює Tier 3, виділяє інвесторів і партнерів, відмічає дублі.
2. Кожен лід, що лишився, перевірити на відповідність **усім активним модулям**. Лід може підходити під кілька модулів.
3. Для кожного збігу — «Базово підходить». Якщо даних замало, поле лишається порожнім (відповідає Tier 4 зі старих правил, тобто «потрібна перевірка»).

**Етап 2** (пошук і перевірка сайту та сторінки компанії в LinkedIn для тих, хто пройшов фільтр без сайту чи опису): факти про компанію — продукт, HQ, розмір, CEO/CTO, сторінки команди й кар'єри. Tier не ставиться.

**Етап 3** (сайт, сторінка кар'єри, новини): для лідів з галочкою і порожніх зібрати **сигнали з модулів**, які збіглися, і визначити Tier 1 або Tier 2.

**Етап 4**: ручна перевірка Tier 1 лідгеном. **Етап 5**: меседжинг (окреме повідомлення під кожного ліда).

**Головне правило: галузь або тег — привід перевірити, але не доказ.** Потрібен хоча б один конкретний сигнал з опису чи сайту (правило «Сигнал vs. сектор» зі старих Tier Rules).

## 3. Спільне ядро (етап 1 для всіх лідів)

### 3.1 Tier 3 для всіх модулів

| Категорія | Приклади | Коментар у таблиці |
|---|---|---|
| Студенти, інтерни, working students | Student, Intern | «Студент» / «Інтерн» |
| Академія, університети, дослідники | Academia & Student, Researcher, Staff Scientist | «Академія» |
| Держсектор, міністерства, держагенції, політика | Ministry, Business Agency, GIZ | «Держсектор» |
| NGO без software-продукту | | «NGO» |
| Конкуренти: IT-аутсорс і дев-шопи з тим самим стеком | EVNE, аутсорс з UA / PL / IN | «Конкурент (назва)» |
| Фріланс-консультанти, коучі, радники | Startup Advisor, Transformation Architect, Freelance | «Консультант/фріланс» |
| Медіа, відео, подкасти, івенти (як постачальники) | Videographer, Podcast Host, Stage Manager | «Медіа» / «Івенти» |
| Великі корпорати без конкретного digital-проєкту | SAP, Siemens, BMW, Allianz (не-digital ролі) | «Корпорат». Якщо роль digital/innovation/IT — лишити порожнім |
| **Enterprise-гіганти — будь-яка роль, зокрема CIO / CDO / Head of AI** (v0.5) | Siemens, Bosch, Deutsche Telekom, Audi, BMW, Mercedes-Benz, CARIAD, ZF, Schaeffler, BSH, AUMOVIO, UniCredit, Allianz, Munich Re, SAP, Novartis, Diageo, MTU | «Enterprise-гігант — закупівля через procurement і великих інтеграторів». **Виняток:** у pitch людина сама шукає зовнішніх постачальників чи партнерів («strategic partnership», «looking for vendors») → лишити для етапу 3. Гігантів можна передавати партнершіпу |
| Гео поза ICP (див. 3.4) | | «Гео поза ICP (країна)» |
| Людина не є DM **для жодного** активного модуля | | «Не DM (посада); компанія релевантна — шукати DM», якщо компанія цікава |

**Важливо:** DM визначається модулем, а не ядром. Operations Manager не є DM для DEV-модулів, але є DM для AUT-4. Tier 3 «не DM» ставимо лише тоді, коли людина не є DM ні для одного з активних модулів.

### 3.2 Investor

VC, angels, family offices, CVC, PE, venture debt, LP.
Коментар: **тип + назва** («VC: Project A (Seed–Series A)», «Бізнес-ангел», «Venture debt: HSBC Innovation Banking»).
Інвестора з власним digital-продуктом або з портфелем, що відповідає ICP, позначаємо так само Investor, а в коментарі пишемо «є взаємна користь: …» (правило з Tier Rules).

### 3.3 Partner / Partner?

**Partner** — тип зрозумілий і реалістичний; **Partner?** — треба перевірити (можливо, конкурент).
Коментар: **«Тип партнера: …»**.

| Тип партнера | Реалістичність | Приклади |
|---|---|---|
| Дизайн-, UX-, продуктові студії без власної розробки | Висока | |
| Маркетингові, growth-, brand-агенції для стартапів і SMB | Середня–висока | Island Collective |
| Консалтинг без розробки (digital transformation, AI strategy, management) | Середня–висока | scale up (коучинг 20–300 людей) |
| Акселератори й інкубатори з портфелем софтверних стартапів | Середня | BayStartUP, Startup.Tirol, NOI Techpark, Wayra |
| Агенти, ментори, спільноти фаундерів з реальним доступом до tech founders | Середня | FounderAgent |
| Рекрутинг/staffing для tech (суміжний до staff augmentation) | Середня | DeepRec.ai |
| Хмарні вендори, партнерські програми | Середня | AWS, Google Cloud |
| Маленькі західні веб- і дев-агенції без власних розробників (white-label) | Середня | → Partner? до перевірки |
| Юрфірми з VC-практикою, організатори галузевих конференцій | Низька | → Partner? |

Акселератори, імпакт-хаби й екосистемні організації **без портфеля** софтверних стартапів — Tier 3.
**Партнерам і інвесторам не віддаємо офлайн-слоти CEO на конференціях.**

**Передача партнершіпу:** усі рядки з Partner і Partner? після етапу 1 передаються команді партнершіпу окремим списком (фільтр за колонкою Tier) разом з типом партнера в коментарі. Лідген їм не пише. Рішення про контакт, текст і канал ухвалює партнершіп. Перевірку «Partner? — партнер чи конкурент» робить партнершіп або лідген на їхній запит.

### 3.5 Дублі

- Кілька людей з однієї компанії: галочку ставимо лише найкращому DM, іншим пишемо «Дубль компанії, DM — [ім'я]».
- Той самий контакт двічі: «Дубль рядка».

### 3.6 Історія контактів [нове]

Перед фільтрацією звіряємо зі спільною базою акаунтів:
- чинні клієнти й відкриті угоди в CRM не йдуть в аутріч;
- ті, хто відповів «in-house», «вже є підрядник» чи «не зараз», отримують коментар з датою відповіді, і до дати повернення ми їм не пишемо.

## 4. Модулі ICP

Шаблон модуля: хто це → послуги → профіль → DM → ознаки для етапу 1 → сигнали етапу 3 → виключення → Tier у модулі → конференції → гачки для меседжу.

---

### DEV-1 · Ранні фаундери

**Статус:** є в попередніх документах (ICP 1 — Pre-Seed Founder). **За замовчуванням модуль вимкнено** (v0.3), див. «Правило за замовчуванням» нижче.
**Хто це:** фаундер (соло або 2–3 співзасновники) на стадії ідеї, прототипу чи раннього MVP, без власної команди розробки.
**Послуги:** AI Product Development, Custom Software (MVP), Product Discovery, AI Consulting; після запуску — Growth & Support.

| Параметр | Значення |
|---|---|
| Стадія | Pre-seed / бутстреп; часто без робочого прототипу |
| Розмір | 1–5 людей |
| Бюджет | Власні кошти або pre-seed раунд |
| Індустрії | Пріоритетний список (healthtech, fintech, edtech, proptech, marketplace, social, agritech, AI/automation, digital greentech) |

**DM:** Founder, Co-Founder, CEO. Технічний співзасновник (CTO) теж, але тоді потреба менша.

**Ознаки для етапу 1:**
- persona Startup; у pitch є «idea stage», «building our first prototype», «looking for a technical co-founder», «pre-seed», «closing pre-seed», «self-funded», «pre-launch», «EXIST»;
- фаундер-студент із software-продуктом.

**Сигнали етапу 3:**
| Сигнал | Сила | Де шукати |
|---|---|---|
| Прямо шукає tech-партнера або розробників | Сильний | Pitch, «looking for», LinkedIn-пости |
| Pre-seed раунд закрито або грант (EXIST тощо) | Сильний | Новини, сайт, pitch |
| Немає технічного співзасновника | Сильний | Сторінка команди |
| Учасник акселератора | Середній | Сайт, pitch |
| MVP зібраний на no-code / vibe-coding і впирається в ліміти | Середній | Сайт, вакансії |

**Виключення:** немає грошей і немає наміру залучати; hardware або deep biotech без software; сильний CTO-співзасновник і вже є команда.

**Tier у модулі:** Tier 1 — є гроші (раунд або грант) і немає технічної команди; Tier 2 — одне з двох.

**Конференції:** стартап-конференції з великою часткою early-stage (Podim, Startup Fair, EBAN, Bits & Pretzels), акселератори.

**Правило за замовчуванням (v0.3):**
- Pre-seed **без грошей** → Tier 3 з коментарем «ICP 1 (pre-seed)», щоб їх можна було витягнути фільтром під окрему кампанію (AI Product Development / Discovery).
- **Виняток:** є гроші (закритий pre-seed, грант на кшталт EXIST) **і** немає технічного співзасновника → DEV-1, Tier 2, лід іде на етап 3 як звичайний.
- Під окрему кампанію модуль вмикається повністю.

Чому так: ранні стартапи тепер менші й часто будують MVP з AI, а за даними SDA зустрічі з ними рідко переходять у дзвінки (дослідження, вересень 2026). Фаундери з грошима і без CTO — найкраща частина сегмента.

**Гачки:** «зібрали v1 з AI → пілоти впираються в безпеку/інтеграції» (H5); Discovery як перший крок.

### DEV-2 · Tech-компанії, що ростуть

**Статус:** поєднує ICP 2 (Seed/Series A, техборг) і ширший профіль «потрібна зовнішня команда» зі старих Tier Rules [частково нове].
**Хто це:** компанія з робочим продуктом і користувачами (seed – Series B або scaleup). Інженерів бракує, накопичився техборг або треба швидко масштабуватися.
**Послуги:** Dedicated Teams, FD Engineers (AI-фічі, що не доходять до продакшну), Custom Software, Legacy & Product Modernization (техборг), Product Diagnostics (code health check, технічна підготовка до інвестицій), Cloud & DevOps, Growth & Support. Підпрофіль «Private AI»: AI Consulting + Custom Software (власна LLM-інфраструктура).

| Параметр | Значення |
|---|---|
| Стадія | Seed → Series B; scaleup |
| Розмір | ~5–150 людей; власна tech-команда від 0 до ~20 |
| Індустрії | Пріоритетний список + суміжні (logistics, media, cybersecurity, legaltech) як Tier 2 |

**Тип потреби (окрема колонка, v0.3):** модуль не ділиться, але кожен лід отримує тип потреби. Він визначає меседж і послугу:
| Тип потреби | Ознаки | Послуги |
|---|---|---|
| **Команда** | Вакансії інженерів, ріст, раунд | Dedicated Teams, Custom Software |
| **AI до продакшну** | AI-фіча чи пілот є, але не в продакшні; вакансії AI/ML Engineer | FD Engineers |
| **Техборг** | Продукт гальмує, зібраний швидко (AI-інструменти), розчарування в підряднику, due diligence перед раундом | Product Diagnostics, Legacy & Product Modernization, Cloud & DevOps |
| **Private AI** | Інтенсивне використання LLM API, регульований домен, 15+ людей на ChatGPT/Copilot | AI Consulting, Custom Software |

**DM:** CEO, Founder, CTO, VP/Head of Engineering, CPO / Head of Product. Прийнятно: COO (у стартапах), Head of Technology. Для «Private AI»: CFO, COO, Head of IT.

**Ознаки для етапу 1:**
- persona Startup або Scaleup, продукт software-first (є опис продукту: platform, SaaS, app, API, AI);
- у pitch: «scaling», «raising Seed/Series A», «fundraising to scale», «live product», «customers», «expanding to [ринок]»;
- немає ознак ідеї чи pre-seed.

**Сигнали етапу 3:**
| Сигнал | Сила | Де шукати |
|---|---|---|
| Раунд за останні 12 міс | Сильний | Новини, Dealroom/Crunchbase, сайт |
| Відкриті вакансії інженерів (особливо кілька одночасно або давно відкриті) | Сильний | Сторінка кар'єри, LinkedIn Jobs, Wellfound |
| Немає CTO або CTO — не технічний співзасновник | Сильний | Сторінка команди |
| Перехід від пілотів до ширшого запуску, вихід на нові ринки | Середній | Новини, сайт |
| Продукт «гальмує» при рості, відомі проблеми зі стабільністю | Середній | Відгуки, статус-сторінка, пости |
| Раунд попереду, треба привести техніку до ладу (due diligence) | Середній | Pitch, новини |

## 5. Перетини ICP і вибір основного

- Лід може збігатися з кількома модулями. Усі збіги записуємо в колонку «ICP-збіги».
- **Основний ICP:**
  1. модуль з найвищим Tier;
  2. якщо Tier однаковий — модуль, під який ця конференція (див. розділ 6);
  3. якщо і це однаково — порядок за замовчуванням (v0.3):
     - стартап- і scaleup-конференції: DEV-2 > DEV-3 > IOT-6 > AUT-4 > MOD-5 > DEV-1;
     - галузеві конференції: AUT-4 > MOD-5 > IOT-6 > DEV-2 > DEV-3.

  Середній чек не використовуємо: великий чек MOD-5 означає й довгий цикл, а конференції потрібні для швидких зустрічей і pipeline. Критерій «чи є в SDA релевантний кейс» поки не використовуємо, бо база кейсів ще формується. Коли вона буде готова, його можна додати третім кроком.
- Повідомлення пишемо під основний ICP. Друга послуга — лише у фоллоу-апі або на зустрічі.
- Одна людина не отримує двох різних повідомлень від SDA.

## 6. Які модулі вмикати під тип конференції

Вторинні (лише явні збіги): MOD-5 — корпорат з digital/IT/innovation роллю; AUT-4 — власник традиційного SMB або Operations Manager. DEV-1 — лише виняток (є гроші, немає CTO) |

| Галузеві tech (fintech, health, proptech) | FINTECH Poland Expo, HLTH Europe, EHiN, Oslo Proptech | DEV-2, DEV-3, MOD-5, AUT-4 |

Що менше активних модулів, то дешевше обробка і менше шуму. Модулі, що не підходять конференції, не вмикаємо.

**Основні модулі** перевіряємо повністю. **Вторинні** — лише для явних збігів, щоб не пропускати корпорати й традиційний бізнес, які теж приїжджають на стартап-конференції.

## 7. Поля таблиці на виході

| Колонка | Значення |
|---|---|
| Базово підходить | TRUE — збіг хоча б з одним модулем; FALSE — Tier 3 / Investor / Partner; порожньо — потрібна перевірка |
| ICP-збіги | DEV-2, AUT-4… |
| Основний ICP | Один модуль |
| Напрям | AI & Software Development / Modernization & Strategy / Automation / Team Extension |
| Тип потреби | Лише для DEV-2: команда / техборг / Private AI |
| Tier | Tier 1 / Tier 2 (після етапу 3); Tier 3 / Investor / Partner / Partner? (етап 1) |
| Коментар з причиною | Чому саме цей ICP або категорія, тип партнера чи фонду, що перевірити |
| Сигнали (етап 3) | Колонки під сигнали основного ICP: значення «так / ні / невідомо» + посилання на доказ |
| Гачок для меседжу | Одне речення, перевірене людиною |

Вкладки для напрямів — це фільтри за колонкою «Основний ICP», а не окремі копії даних.

## 8. Рішення і відкриті питання

**Вирішено:**
1. **Перелік ICP:** 6 модулів; DEV-2 не ділимо, додано колонку «Тип потреби» (v0.3).
2. **DEV-1:** за замовчуванням вимкнено; виняток — є гроші і немає технічного співзасновника (v0.3).
3. **MOD-5:** SDA готова до enterprise, модуль активний (v0.2).
4. **IOT-6:** межа — пристрій + застосунок/платформа, без прошивки, space, енергетичного «заліза», лабораторного біотеху, зброї (v0.3).
5. **Гео для AUT-4:** пріоритет Nordics/UK/US/AU; DACH і ЄС — прийнятні, максимум Tier 2 (v0.3).
6. **FD Engineers:** виділений інженер SDA в команді клієнта для AI-автоматизації; основні ICP — AUT-4 і MOD-5, другорядний — DEV-2 (v0.4, за сторінкою послуги).
7. **Основний ICP:** Tier → фокус конференції → порядок за замовчуванням; середній чек і наявність кейсу не використовуємо (v0.3).
8. **Партнери:** є партнершіп, Partner / Partner? передаються йому (v0.2).
9. **Enterprise-гіганти:** Tier 3 для всіх модулів (немає виходу на procurement), крім людей, які в застосунку самі шукають постачальників; ціль MOD-5 — великий Mittelstand (v0.5).

**За замовчуванням до підтвердження:**
- **Оборона та dual-use в IOT-6:** поки лишаємо з коментарем, рішення за керівництвом.
- **Облікове ПЗ для DACH і ЄС (AUT-4):** потрібне коротке дослідження (наприклад, чи поширені DATEV, lexoffice, sevDesk). Після нього DACH може отримувати Tier 1.
- **Кейси:** коли база кейсів буде готова, додати «наявність релевантного кейсу» у правило вибору основного ICP.
